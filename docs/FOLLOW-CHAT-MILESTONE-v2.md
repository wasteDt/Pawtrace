# 关注与会话优先方案 v2

> 状态：关系规则已确认，聊天媒体范围待确认，正在按阶段实施。用户最新决定优先于旧版 PRD 中“不做私信/实时聊天室”和“个人提问采用异步问答页”的描述。旧版 [健康问答阶段方案](HEALTH-QA-MILESTONE-v1.md) 暂停实施，公开问题仍计划在后续论坛阶段完成。

## 1. 新的产品顺序

1. **关注与好友列表**：先有可访问的公开主页、关注/粉丝列表，以及明确的好友关系。
2. **实时聊天室与消息页**：好友间以会话形式交流；消息页每个联系人只显示一条会话摘要，进入后查看完整消息时间线。
3. **向医生个人提问**：从认证医生主页进入私密会话，使用有结构的“宠物健康提问卡”提供宠物、症状、主动选择的病史及图片/视频；后续追问在该会话中继续，不再创建独立的个人问答帖子。
4. **公开健康问答论坛**：宠物主人发布公开问题，认证医生在论坛详情回答；这与私密会话是两种不同的信息形态，不能混入同一个公开列表。

本阶段先交付第 1、2 项，并把第 3 项所需的会话权限和数据边界设计好；医生提问卡及公开论坛在后续子阶段逐步实现，不把“普通聊天消息”误当完整医疗提问功能。

## 2. 已确认的关系规则

“关注”是单向关系，“好友”特指互相关注；两者不是同一状态。

| 决策 | 已确认规则 |
| --- | --- | --- |
| 普通用户何时能聊天 | 关注对方即可主动发起一对一聊天。会话建立后双方都可回复；若双方均取消关注，则暂停发送但保留历史。发给对方的每条消息仍受对方当前接收设置约束。 |
| 接收消息设置 | 默认允许已有单向关注关系的会话双方继续聊天；用户可在“设置 → 消息隐私”切换为“仅接收互相关注用户的消息”。切换即时生效，保留历史消息但阻止不符合规则的新消息。新会话仍由关注对方的一方发起。 |
| 向医生提问是否要求好友关系 | 不需要关注或互关；从当前认证医生主页发起私密健康提问，具体接诊交互留待健康提问卡子阶段确定。 |

关注本身**不会**自动公开手机号、宠物档案或病史，也不会授予医生回答或查看病史的权限。医生的专业权限始终由后端当前认证状态决定。聊天权限由服务端在**每次发消息时**依据发送者关注关系、接收者设置和账号状态重新校验，不只在创建会话时校验。

## 3. 消息页：会话不是通知流水账

用户端顶部“收件箱”调整为“消息”。消息页分为两个清晰区域：

| 区域 | 一行代表什么 | 未读数与实时更新 |
| --- | --- | --- |
| 会话 | 一个联系人对应一个会话入口，展示头像、名称、最后一条消息摘要、时间和该会话未读数；同一人的 20 条消息仍只占一行 | 收到新消息时该会话置顶并更新未读数；打开会话后按已读游标清零 |
| 系统通知 | 认证结果、身份撤销、平台公告等平台事件；延用当前收件箱能力 | 仍可按事件展示，但不为每条聊天消息额外生成一条 `UserNotification` |

顶部角标可以显示“未读会话消息数 + 未读系统通知数”，进入消息页后分别标明两类数量。管理端工作通知仍保留在管理端，不与前台聊天混合。首版支持将会话从自己的列表隐藏；隐藏只影响自己的列表，不删除对方消息，新消息到来时可重新出现。会话静音和长列表分页属于后续增强。

实时机制沿用当前技术栈：发消息用带会话/CSRF 校验的 HTTP 请求；服务端先持久化，再经 SSE 向会话成员推送“新消息/会话摘要更新”。断线重连后从数据库按游标补取遗漏消息。当前单实例可复用进程内连接管理；多实例时需共享事件通道。**SSE 是推送通道，数据库才是消息与未读状态的可靠来源。**

## 4. 页面与交互

| 页面/入口 | 第一交付内容 |
| --- | --- |
| 用户/医生公开主页 | 公开昵称或医生展示名、当前认证标识、机构/擅长领域、关注按钮；不暴露真实姓名、手机号、认证材料、病史 |
| 我的关注 | “关注的人”“粉丝”“好友”列表，人数及取消关注；好友判定取决于第 2 节选择 |
| 消息列表 | 会话与系统通知分区/标签，最近消息、未读数、隐藏、空态、离线补齐；静音与长列表分页后续补充 |
| 聊天窗口 | 历史消息分页、实时新消息、发送状态、已读位置、错误提示；默认先交付文字聊天，自动重试后续补充 |
| 医生主页提问入口 | 后续子阶段加入；医生认证失效时不能发起新的健康提问 |

普通聊天的首版媒体范围仍待确认；文字消息与实时/离线会话能力先作为基础交付。图片/视频上传属于医疗提问卡和论坛发布时的独立媒体能力，仍按既定“图片最多 9 张 + 视频最多 1 个”规则设计，不因为先上聊天而取消视频需求。

## 5. 数据与后端边界

基于当前 MySQL + Prisma 模型新增以下领域，不把聊天消息塞入 `UserNotification`：

| 模型 | 职责 |
| --- | --- |
| `Follow` | `followerId` 与 `followingId` 唯一组合；禁止自关注，取消关注幂等；好友关系按确认后的规则派生或记录 |
| `Conversation` | 会话 ID、会话类别、最后消息与最后活动时间；普通一对一会话应有稳定唯一标识，避免同一对用户产生多条并列会话 |
| `ConversationParticipant` | 成员、已读游标、静音、隐藏时间；每个成员只维护自己的列表和未读状态 |
| `ChatMessage` | 会话、发送者、消息序号/时间、类型、正文或受控业务卡片引用、删除状态；接收人不能伪造发送者 |
| 后续健康提问卡 | 关联宠物、目标医生、症状与主动共享的病史/媒体；病史仍单独鉴权，不能把完整病史正文复制到普通聊天摘要 |

第一交付接口可按领域拆为 `/users/:userId/follow`、`/me/following`、`/me/followers`、`/me/friends`、`/conversations`、`/conversations/:id/messages`、`/conversations/:id/read`、`/conversations/stream`。具体请求字段、分页游标和错误码在实施前写入 API 设计，并对“未登录、非成员、非好友、账号禁用、身份撤销”逐项校验。

私密会话仅成员可查；会话列表不能泄露其他人的联系人或聊天摘要。媒体访问、医生健康提问卡和病史共享在后续子阶段按业务对象鉴权，不能因为两人是好友就自动开放。发消息设置频率限制与长度限制；删除/隐藏应区分“仅对我隐藏”与真正撤回，第一交付不做双向删除历史。

## 6. 医生个人提问如何进入会话（后续子阶段）

医生提问不是一段没有上下文的普通文字。建议在会话中发送一张结构化的**健康提问卡**：主人主动选择自己的宠物，填写症状和持续时间，可选共享指定病史、图片及视频；医生在会话内回复和追问。卡片与附件只允许作者和被指定的**当前认证宠物医生**读取，医生助理不能接收或查看。

这张卡片只会出现在与该医生的私密会话，不进入公开论坛、公共搜索或系统通知正文。通知只包含“收到新的健康提问”及受控跳转，不复制症状、病史或媒体地址。若医生认证被撤销，健康卡片及共享病史立即停止向其开放；普通好友聊天是否保留由关系规则决定。作者保留查看历史记录的能力，暂不自动转派医生。

## 7. 实施顺序与验收

1. 按第 2 节的已确认关系规则实施，并同步修订旧 PRD/交互/API 文档中“无私信、个人提问走异步问答页”的冲突内容。
2. 完成关注与公开主页、关注/粉丝/好友列表；校验自关注、重复关注、账号禁用与取消关注。
3. 完成一对一会话、消息持久化、会话列表、已读游标、实时推送与离线补齐；同一联系人只有一条列表入口。
4. 将现有前台通知界面调整为“会话 / 系统通知”；管理员工作收件箱保持独立。聊天消息不得生成逐条系统通知。
5. 再接入医生健康提问卡，最后实现公开健康问答论坛。

第一交付验收重点：两个已授权聊天的用户可互发消息；在线即时到达，离线重登后不丢；同一联系人连续发 20 条消息，消息页仍只显示**一条会话**，未读数正确；打开后已读状态持久化；非成员无法读写该会话；取消关注或身份变化后的行为符合已确认规则；管理端通知与用户会话互不混淆。
