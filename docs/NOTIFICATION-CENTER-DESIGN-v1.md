# Pawtrace 通知中心设计 v1

## 1. 目标

通知中心同时解决两类需求：

- 用户及时得知认证结果、问答回复、互动和平台通知。
- 管理员及时得知新的治理任务、待办变化和系统风险。

通知不能只存在于临时弹窗中。数据库记录是可靠来源，SSE 只负责实时提醒；断线或离线后重新进入仍能补齐消息。

## 2. 统一交互结构

用户端和管理端都采用两层入口：

1. 顶部铃铛：展示未读数量和最近 5 条消息，用于快速查看。
2. 独立通知中心：展示完整列表、分类、已读状态和操作入口。

实时消息到达时：

- 更新铃铛未读数。
- 将新消息插入最近消息顶部。
- 显示轻量 Toast，不强制打断当前操作。
- 如果通知中心正打开，直接插入列表，无需刷新。

## 3. 用户通知中心

### 3.1 分类

- 全部。
- 未读。
- 身份认证：申请通过、驳回、身份撤销、身份恢复。
- 问答消息：医生回答、追问、问题状态变化。
- 社区互动：评论、回复、关注。
- 系统消息：公告、安全和服务提示。

第一阶段实现全部、未读、身份认证、系统消息；其余类型随业务模块接入。

### 3.2 列表字段

- 消息图标和分类。
- 标题、摘要、产生时间。
- 已读/未读状态。
- 受控业务跳转。

列表按时间倒序。点击消息时先标记已读，再跳转到站内目标。无跳转目标的消息只展开内容。

### 3.3 操作规则

- 单条标记已读。
- 全部标记已读。
- 第一版不允许彻底删除系统通知，避免重要治理信息丢失。
- 后续可以增加归档，不与已读状态混用。
- 未读数量以服务端数据库为准，前端实时更新后定期重新校准。

## 4. 管理员通知中心

管理员通知与普通用户通知分表存储，不能发送到前台用户收件箱。

### 4.1 分类

- 工作待办：新的专业认证申请、新举报、需要复核的内容。
- 状态变化：申请人撤销申请、任务被其他管理员处理。
- 系统提醒：服务异常、上传失败率和安全风险。
- 平台通知：管理员公告和规则调整。

第一阶段接入专业认证工作流：

- 用户提交认证申请时，所有启用的管理员收到工作通知。
- 点击通知进入认证申请页。
- 申请被处理后通知保留，业务页面显示实际状态；通知本身不等同于待办状态。
- 工作台待办数字通过业务数据实时统计，不通过未读通知数推断。

### 4.2 管理端交互

- 顶部栏增加通知铃铛和未读角标。
- 弹层展示最近 5 条以及“查看全部”。
- 侧边导航增加“通知中心”。
- 通知中心支持全部、未读、工作待办、系统提醒筛选。
- 单条已读和全部已读均写入数据库。

## 5. 数据与安全

- 用户通知关联 `userId`；管理员通知关联 `adminUserId`。
- 通知只存摘要和受控站内链接，不存证明材料地址、病史、病例正文或完整手机号。
- 读取、标记已读和实时连接都必须验证各自 Session。
- 前台和后台使用不同的 SSE 地址与 Session Cookie。
- SSE 响应关闭 Nginx 缓冲并发送心跳；断线由 `EventSource` 自动重连。
- 多实例部署时，内存推送需要替换为 Redis Pub/Sub；当前单实例 MVP 使用进程内连接表，数据库保证消息不丢失。

## 6. 第一阶段接口

### 用户端

- `GET /api/v1/me/notifications?filter=all|unread|professional|system`
- `POST /api/v1/me/notifications/:id/read`
- `POST /api/v1/me/notifications/read-all`
- `GET /api/v1/me/notifications/stream`

### 管理端

- `GET /api/v1/admin/notifications?filter=all|unread|work|system`
- `POST /api/v1/admin/notifications/:id/read`
- `POST /api/v1/admin/notifications/read-all`
- `GET /api/v1/admin/notifications/stream`

## 7. 验收标准

- 用户和管理员均有独立通知中心与顶部快捷入口。
- 新认证申请提交后，在线管理员无需刷新即可看到角标和新消息。
- 认证处理后，在线用户无需刷新即可收到结果。
- 双方离线后重新登录仍能看到完整消息。
- 点击消息可以进入正确业务页面并减少未读数。
- 全部已读操作刷新后仍然有效。
- 通知未读数与工作台待办数语义清晰、互不混用。
