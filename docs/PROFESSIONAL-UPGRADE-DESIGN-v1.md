# 医生助理升级宠物医生：交互与状态流转 v1

## 1. 目标与范围

解决已认证医生助理无法继续申请宠物医生身份的问题。用户仍只有一个普通账户和一个**当前生效的专业身份**；升级申请是对现有身份的变更请求，不会立即改变权限。

本阶段只处理 `已认证医生助理 → 宠物医生`。首次认证、管理员撤销/恢复身份继续使用现有流程；医生降级助理、同身份重复认证、资料修改、被撤销后的重新认证不纳入本阶段的交互实现。同身份重复认证应由后端明确拒绝，而不是当成资料修改。

本文细化现有 [交互流程](UX-FLOW-v1.md) 中“升级审核期间原身份继续有效”的规则，以及 [管理后台规划](ADMIN-CONSOLE-PLAN-v1.md) 中“管理员不能直接修改身份类型”的规则。它是下一步实现依据，**不是已上线功能说明**。

## 2. 核心规则

1. 只有 `ProfessionalProfile(type=ASSISTANT, status=APPROVED)` 的用户可以发起升级，目标固定为 `VETERINARIAN`。普通用户走首次认证；已认证医生无升级入口。
2. 同一用户任意时刻最多一笔 `PENDING` 认证申请。升级申请提交后不能在审核中改成其他身份；如需更换材料，先撤回再重新提交。
3. 升级待审、驳回或由本人撤回期间，原助理身份和权限保持有效；只有审核通过且事务提交成功后，才切换为医生权限及认证标识。
4. 升级必须重新上传执业兽医资格证。之前用于助理认证的学历材料不能自动代替；证明文件依旧仅申请人及有审核权限的管理员可访问。
5. 管理员只对申请做通过/驳回，不能通过“恢复身份”或直接编辑资料将助理改为医生。审核和身份切换必须有理由、审计记录及通知。
6. 管理员撤销助理身份时，如存在待审升级申请，须在同一事务中取消该申请；不得在已撤销身份上继续通过升级。被撤销后的**重新认证**沿用既有产品规划，但作为另一条流程另行设计，不能复用“助理升级”入口绕过撤销。

## 3. 状态与权限

`ProfessionalApplication` 记录一次申请的审核结果；`ProfessionalProfile` 记录当前有效身份。两者不可混为一个状态。建议在申请中记录用途 `INITIAL` / `UPGRADE`，以及提交时的原身份快照 `ASSISTANT`，便于管理员识别和事后追溯；具体字段名可在实施时与现有数据库命名统一。

| 场景 | 当前身份 `ProfessionalProfile` | 升级申请 | 用户可用权限与页面标识 |
| --- | --- | --- | --- |
| 升级前 | `ASSISTANT / APPROVED` | 无 | 医生助理权限；显示助理标识和“申请升级” |
| 已提交、待审核 | `ASSISTANT / APPROVED` | `UPGRADE / PENDING` | 仍是助理；显示审核进度、目标身份和撤回入口 |
| 审核驳回 | `ASSISTANT / APPROVED` | `UPGRADE / REJECTED` | 仍是助理；显示驳回理由和“重新申请升级” |
| 本人撤回 | `ASSISTANT / APPROVED` | `UPGRADE / CANCELLED` | 仍是助理；可再次申请升级 |
| 审核通过 | `VETERINARIAN / APPROVED` | `UPGRADE / APPROVED` | 医生权限；显示医生标识，不再显示升级入口 |
| 待审时助理身份被撤销 | `ASSISTANT / REVOKED` | `UPGRADE / CANCELLED` | 专业权限失效；升级入口关闭，另走重新认证流程 |

状态流转如下，审核结果不可在同一笔申请上反复修改：

```text
助理身份 APPROVED
  └─提交升级→ 申请 PENDING（助理身份保持 APPROVED）
                 ├─本人撤回→ CANCELLED（保持助理）
                 ├─管理员驳回→ REJECTED（保持助理，可新建申请）
                 ├─管理员通过→ APPROVED（身份原子切换为医生）
                 └─助理身份被撤销→ CANCELLED（身份变为 REVOKED）
```

## 4. 用户端交互

入口沿用“我的 → 专业身份认证”。页面不能只根据 `profile.status=APPROVED` 就结束渲染；必须同时展示**当前身份**和**最新升级申请**。

| 页面状态 | 展示与操作 |
| --- | --- |
| 已认证助理、无待审升级 | 顶部显示“当前身份：认证医生助理”，说明现有权限；提供“申请升级为宠物医生”按钮。点击后打开目标锁定为医生的申请表。 |
| 填写升级资料 | 可预填已有展示名称、机构、擅长领域等可编辑资料；明确标出“需重新上传执业兽医资格证”，未选择文件不能提交。提交前说明“审核期间保持医生助理身份，审核通过后切换为宠物医生”。 |
| 升级审核中 | 同时显示“当前身份：医生助理”和“升级申请：审核中”。提供材料名称、提交时间与“撤回申请”；不提供重复提交或切换申请类型。撤回前二次确认，并明确不会撤销已有助理身份。 |
| 升级被驳回 | 保留助理身份卡，展示本次驳回理由；允许修正资料、新传证明并发起**一笔新的**升级申请。历史驳回记录保留。 |
| 升级已通过 | 刷新当前身份为医生；成功消息说明已获得医生权限，助理升级按钮消失。 |
| 升级申请被撤回 | 返回助理身份卡，可重新申请；提示“撤回的是升级申请，医生助理身份未受影响”。 |

认证状态在页面进入、申请提交/撤回、收到审核通知后重新获取；前端即时展示以服务端返回状态为准，不根据本地按钮点击推测权限变化。

## 5. 管理端交互

“认证申请”列表与详情明确标记申请用途“首次认证 / 助理升级医生”，并同时显示**当前有效身份**和**申请目标身份**，避免审核员把升级误当首次申请。审核材料为本次提交的执业兽医资格证，不用旧助理材料代替。

- 审核通过前再次确认：申请仍为 `PENDING`，申请人当前仍是 `ASSISTANT / APPROVED`；若不满足，返回状态冲突并提示刷新，不直接覆盖身份。
- 驳回必须填写理由；通过也沿用项目现有的审核说明/审计要求。成功后列表状态与详情同步更新。
- 管理员对已认证助理执行“撤销身份”时，如有待审升级，确认文案说明申请也将取消；事务完成后两个状态同步变化。
- 本人撤回待审升级后，管理员待办应及时消失，并产生申请取消的工作提醒。现有代码仅改变申请状态，尚未写入这条管理员消息，实施时一并补齐。

## 6. 后端与数据约束

沿用现有 `POST /api/v1/professional-applications`、`POST /:applicationId/cancel`、管理员审核接口和 `GET /api/v1/me/professional-profile`；扩展业务校验及响应字段，不新增一套脱离现有认证模型的“升级身份”接口。

| 操作 | 服务端必须保障 |
| --- | --- |
| 提交 | 根据当前身份判断首次认证还是升级；升级只能从有效助理指向医生；有待审申请、已是医生、申请同身份或试图降级都返回明确的业务错误。提交和“是否已有待审申请”的校验需处理并发，不能只依赖前端禁用按钮。 |
| 撤回 | 只有本人可撤回自己的 `PENDING` 申请；撤回升级不得修改当前助理身份。若管理员已审核，则返回状态冲突，不把审核结果改回取消。 |
| 审核 | 在事务内条件性地取得待审申请并核对当前身份；同一申请只能成功审核一次。通过升级时原子地把 `ProfessionalProfile.type` 改为 `VETERINARIAN`，同时记录审核、审计和用户通知；驳回时不改当前助理身份。 |
| 撤销身份 | 原子地撤销当前身份并取消仍待审的升级申请；审核请求若与撤销并发，只能有一个符合其前置条件并成功，另一方收到冲突提示。 |
| 消息 | 申请提交提醒管理员；撤回提醒管理员；审核结果通知用户。消息正文只写身份与结果摘要，不包含证件文件、真实姓名等敏感材料。入库后再使用现有 SSE 推送，断线后仍可从收件箱读取。 |

申请用途应由服务端按**提交时的当前身份**确定并保存，不能信任客户端传来的 `applicationPurpose`。原身份快照也由服务端写入。现有 `ProfessionalApplication` 记录申请历史、`ProfessionalProfile` 保存当前身份的设计可以保留；实施时需要数据库迁移、前后端类型及接口响应同步调整。

## 7. 与当前代码的差距

- [`ProfessionalView.tsx`](../frontend/src/components/public/ProfessionalView.tsx) 在 `profile.status === "APPROVED"` 时只渲染成功卡片，导致助理没有升级入口，也看不到同时存在的待审升级。
- [`professional-applications.ts`](../backend/src/routes/professional-applications.ts) 只拦截已有 `PENDING` 申请，没有按当前有效身份限制升级方向、同身份重申或医生降级。
- [`admin-professionals.ts`](../backend/src/routes/admin-professionals.ts) 审核通过时直接 `upsert` 并覆盖身份类型；缺少升级前置状态的并发核对。现有撤销逻辑已取消待审申请，但需要与升级审核竞争条件一起验证。
- 当前申请数据没有显式“首次/升级”用途快照；管理员页面和用户通知也未区分两种申请。
- 当前用户撤回申请只更新申请状态，没有生成管理员工作提醒。

## 8. 验收场景

1. 已认证助理能看到升级入口；医生和未认证用户看不到该入口，未认证用户仍可走首次认证。
2. 助理提交正确资料后，页面同时显示有效助理身份和待审医生申请；助理专业权限仍可使用，医生专属权限不能提前使用。
3. 同一用户重复提交、申请相同身份或试图医生降级助理，前后端都给出清晰结果，数据库不产生错误申请。
4. 管理员通过后，当前身份仅有一个且为医生；用户实时收到结果，刷新后仍是医生，历史助理申请和升级申请均可追溯。
5. 管理员驳回后，助理身份不变；用户看到理由，可上传新材料重新申请。
6. 用户撤回后，助理身份不变；管理员待办消失并收到取消提醒；已审核申请无法再撤回。
7. 助理身份在待审升级时被撤销，升级同步取消；管理员无法随后通过旧申请，用户专业权限立即失效。
8. 两名管理员同时审核，或审核与撤回/撤销同时发生时，至多一个终态成功，不出现申请结果与当前身份互相矛盾的情况。
